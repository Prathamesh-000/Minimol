# Minimol 2026 — P2P Mobile Mesh Inference (implementation starter)

## What is already implemented?
- A 6-layer, 11,040,768-parameter **provisional** PyTorch reference with seed 42.
- Deterministic FP32 `weights.bin` export plus independent Phone 1 and Phone 2 shards.
- SHA-256-checked tensor manifest and test fixtures.
- Real CPU-only JavaScript inference with 3 transformer blocks per phone, causal incremental attention/KV caches, byte embedding and greedy output head.
- Direct WebRTC DataChannel with **no STUN/TURN configured**, compressed QR/manual SDP offer/answer, binary 1,552-byte activation frames, run sequencing.
- A first-pass static website for two phones. It is **NOT proven universal on iOS/Android**, and is not yet performance optimized.

## Non-negotiable warning
The official statement does not define the complete model code, initialization order, normalization choice, GELU variant or file ordering. Our design is an **explicit provisional choice** that hits the exact count. Python/JS match our own golden vectors; this does **not** prove parity with a hidden organizer reference. Ask organizers for canonical code/hash and update the exporter/reference + fixtures if they provide it.

## Run locally — development machine
```bash
# From the repository root:
python -m venv .venv
source .venv/bin/activate  # on Windows: .venv\\Scripts\\activate
pip install -r ml/requirements.txt
PYTHONPATH=ml pytest -q ml/test_reference.py
python ml/export_weights.py

cd web
npm install
npm test
npm run parity
npm run dev
```
The exporter produces `web/public/model/{manifest.json,phone1.bin,phone2.bin,fixtures.json}` and `ml/artifacts/weights.bin`. Do not commit large binaries until your team agrees whether to use Git LFS / Releases / static hosting. Each phone loads only its shard.

## Two real phones — staging
1. **Deploy the built static website at an HTTPS site root.** From `web`, run `npm run build`; publish `web/dist` on a static host (e.g. Cloudflare Pages or Netlify) with no backend. Assets must be served at `/model/...`. The host serves static files only; it must not perform inference.
2. Phones join the **same Wi-Fi network** (router must allow client-to-client traffic). Both open the same HTTPS URL and fully load their model shard.
3. Phone 1 chooses Phone 1 and presses **Create offer QR**.
4. Phone 2 chooses Phone 2, scans Phone 1's QR and shows an **answer QR**.
5. Phone 1 scans Phone 2's answer QR. Wait for both to display a matching model hash and connected DataChannel.
6. Phone 1 starts a short prompt (e.g. `Hi`, 3 generated bytes). Phone 2 computes the other three layers.
7. For offline mode **after both pages/assets are loaded**, unplug the router's WAN/internet while keeping the Wi-Fi LAN powered. Do NOT turn off the phones' Wi-Fi. Generate again and confirm the local WebRTC link remains.

If QR size/scanning fails, the `MINIMOL1:...` signal can be pasted into the other phone. That is a fallback only: robust multi-frame QR and real-device validation remain Member 3's task. A QR or copy/paste exchange is *signaling* only; inference activation bytes must use direct WebRTC.

**Reference parity already verified in the authoring environment:** maximum absolute cut/logit deviation approximately `0.000001`; predicted bytes matched on `A`, `Hi`, `Mesh`, and non-ASCII `é` fixtures. No physical smartphone/HTTPS deployment test has been performed in that environment.

## Frozen first milestone
- Two phones exchange one `1552`-byte frame over direct WebRTC.
- Phone 1 generates cut activations from blocks 0–2; Phone 2 runs 3–5 and returns greedy byte.
- Test `Hi` produces the provisional reference byte sequence `[30,18,116]` for three new bytes.
- Both phones use exact validated per-phone shards; neither loads full model.
